## 摘要
大语言模型（LLMs）越来越多地被部署为智能体，在多个步骤中与有状态环境交互：收集隐藏信息、组合工具调用以及提交状态更改。我们将这种能力称为多步骤工具使用。现有的基准测试推动了工具使用智能体的评估，但通常侧重于孤立的API调用、短轨迹或难以扩展或控制的设置。我们引入了E-Bench，这是一个完全合成的基准测试，包含323个状态更改任务，涵盖三个产品领域：王者荣耀、QQ音乐和腾讯会议。E-Bench将环境合成与任务合成解耦：基于图引导的数据库填充构建可重用、无孤立的产品环境，而生成器-求解器不对称性创建的任务既有信息缺口也有工具缺口，要求智能体在更改状态前发现隐藏数据并组合多个工具调用。结果通过数据库状态差异进行确定性评分。由于环境和任务都是合成的，E-Bench在环境层面可控，在任务层面可扩展。对11种前沿大语言模型的基准测试表明，多步骤工具使用仍然具有挑战性：最强模型的Pass^3仍低于60%，即使在E-Bench-Code扩展中使用代码执行，可靠性（Pass^3）仍低于70%。

## Abstract
Large Language Models (LLMs) are increasingly deployed as agents that interact with stateful environments over multiple steps: gathering hidden information, composing tool calls, and committing state changes. We refer to this capability as multi-step tool use. Existing benchmarks have advanced tool-use agent evaluation, but often focus on isolated API calls, short trajectories, or settings that are difficult to scale or control. We introduce E-Bench, a fully synthetic benchmark with 323 state-changing tasks across three product domains: Honor of Kings, QQ Music, and Tencent Meeting. E-Bench decouples environment synthesis from task synthesis: graph-guided database filling builds reusable, orphan-free product environments, while generator-solver asymmetry creates tasks with both an information gap and a tool gap, requiring agents to discover hidden data and compose multiple tool calls before changing state. Outcomes are graded deterministically by database-state diffs. Since both environments and tasks are synthetic, E-Bench is controllable at the environment level and scalable at the task level. Benchmarking 11 cutting-edge LLMs shows that multi-step tool use remains challenging: Pass^3 stays below 60% for the strongest models, and even with code execution in the E-Bench-Code extension, reliability (Pass^3) remains below 70%.

## 2. 论文提出的方法论

**核心思想**  
将**环境合成**与**任务合成**彻底解耦，构建一个共享的、可复用的全合成产品环境，再基于该环境自动生成带有“信息缺口”和“工具缺口”的状态变更任务。

**关键技术细节**

- **环境合成（图引导数据库填充）**
  - 将产品领域建模为关系型数据库，构建表级依赖图。
  - 按拓扑序、在强外键约束下逐表填充：根表先生成，子表基于已存在的父记录生成，保证**无孤儿记录**。
  - 使用强大 LLM 作为约束式合成器，每次生成均在工具交互中完成插入，并由数据库强制执行主键与外键完整性。
  - 合成后进行确定性脚本验证与修复，确保跨表、跨字段语义一致性。
  - 最终在数据库之上构建**领域专用 MCP 工具**（CRUD 接口），提供产品级语义的操作（如搜索歌曲、创建会议等）。

- **任务合成（生成器‑求解器不对称）**
  - **信息缺口**：任务生成器可访问完整数据库（拥有查询 SQL 权限），而求解器只能通过领域工具获取观察，迫使智能体主动探索隐藏状态。
  - **工具缺口**：生成器可使用代码执行（`exec_code`）进行分页、聚合、集合操作，而求解器在基础设定中不可执行代码，必须通过链式或并行工具调用完成同等计算。
  - 生成器按“探查数据 → 决定目标 → 修改状态 → 概括意图”的循环生成任务，记录数据库状态差异作为真实标签。
  - 任务需经过三个强验证器（GPT‑5.5、Opus‑4.8、GLM‑5.1）的重现验证，并过滤掉弱基线模型轻易解决的任务。

- **确定性评分**  
  通过直接对比智能体操作后的数据库状态与真实差异（insert/update/delete）进行**规则式、零容许误差**的评判，不使用 LLM 评判。

- **E‑Bench‑Code 扩展**  
  在基础设定之上授予求解器 `exec_code` 工具，部分关闭工具缺口，仍保留信息缺口，用以量化代码执行对性能天花板的影响。

## 3. 实验设计

- **评测数据集**：E‑Bench 主基准包含 **323 个状态变更任务**，覆盖三个真实产品场景：
  - 王者荣耀（社交、组队、比赛管理）
  - QQ 音乐（内容搜索、偏好与歌单管理）
  - 腾讯会议（组织架构、会议室预定、日程与群组管理）
- **评测模型**：**11 款前沿 LLM**，包括 Kimi‑K3、GPT‑5.5、Opus‑4.8、Grok‑4.5、GLM‑5.2、Qwen‑3.7‑Max、Hy3、Seed‑2.1‑Pro、Gemini‑3.5‑Flash、MiniMax‑M3、DeepSeek‑V4‑Pro，另部分测试了 Muse‑Spark‑1.1。
- **任务执行规范**：每个任务独立执行 3 次试验，每次从全新数据库副本开始；仅在所有试验都达到精确数据库状态差异时才计为成功。
- **核心指标**：
  - **Avg@3**：所有试验的成功率均值。
  - **Pass@3**：至少一次试验成功的任务比例。
  - **Pass³**：三次试验全部成功的任务比例（衡量**可靠性**）。
- **对比维度**：
  - 基础 E‑Bench 与 E‑Bench‑Code 两种设定。
  - 跨领域、跨能力类型（全量数据获取、多条件过滤、聚合计算、跨步依赖、精确边界判断、跨实体级联）的细粒度分析。
  - 效率与成本分析：每任务工具调用数、交互轮数、Token 消耗、API 费用。

## 6. 论文的主要结论与发现

- **多步工具使用远未解决**：最强模型 Kimi‑K3 在 E‑Bench 上的 Avg@3 仅为 73.79%，Pass³ 低于 60%；模型平均水平仅约 54.56%。
- **可靠性是核心瓶颈**：Pass@3 与 Pass³ 之间存在巨大落差，多数模型仅能间歇性完成任务，难以稳定地修改产品状态。
- **代码执行提升性能，但仍不完美**：提供 `exec_code` 后所有模型均有显著增益，Opus‑4.8 的 Avg@3 升至 81.11%，但最强者 Pass³ 仍低于 70%，可靠性提升有限。
- **代码执行获益主要体现在机械计算**：全量数据获取、多条件过滤、聚合计算等密集型任务获益较大，而需推理的精确边界判断、跨步依赖获益较小。
- **代码执行大幅降低交互成本**：工具调用数平均减少 73.8%，交互轮数减少 33.6%，优质模型能在更少回合内完成更复杂的任务。
- **领域难度与模型排序变动显著**：王者荣耀最难，QQ音乐最易；代码执行会打乱排行榜，强代码能力的模型可跃居前列。
- **并行工具调用与 Token 效率强相关**：并行度低的模型因串行执行、反复重读长上下文而产生极高的 Token 消耗。

## 7. 优点：方法或实验设计上的亮点

- **环境‑任务解耦设计**：一次构建环境可反复生成任务，高度可扩展、可复用，避免了传统评测中环境与任务高度耦合的问题。
- **全合成、高可控**：不依赖真实服务，避免了数据安全、隐私和可复现性问题，且可通过控制图填充与任务生成参数调整难度与分布。
- **强制信息缺口与工具缺口**：通过严禁求解器直接访问数据库或代码执行，保证智能体必须通过多步工具调用主动探索和计算，贴合真实 Agent 场景。
- **确定性无偏评分**：基于数据库 diff 的规则验证，杜绝了 LLM 评判的主观性和不稳定性。
- **可靠性导向的严格指标**：引入 Pass³（三次试验全对），强调一致性和鲁棒性，契合实际部署需求。
- **细致的成本‑效率分析**：明确展示各模型在价格、工具调用数、轮次上的权衡，为实际选型提供参考。
- **覆盖多种实际能力**：将任务按信息获取、过滤、聚合、级联、判断等维度分类，有助于定位弱点。

## 8. 不足与局限：包括实验覆盖、偏差风险、应用限制等

- **领域覆盖面有限**：仅基于三个特定的互联网产品（游戏、音乐、会议），是否映射到其他业务域（如金融、医疗、工业软件）有待验证。
